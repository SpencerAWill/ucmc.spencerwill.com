# Site-feedback triage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make site and club feedback explicit in every identifier, turn `/feedback` into a two-card index, and replace the automatic one-issue-per-submission GitHub mirror with in-app triage and saved issue drafts that link many submissions to many GitHub issues.

**Architecture:** `features/feedback` becomes `features/site-feedback`. Two new D1 tables (`site_feedback_issues`, `site_feedback_issue_links`) and an FTS5 index hang off the existing `feedback` table, whose SQL name stays. A small GitHub REST/GraphQL client is called only by deliberate maintainer actions (file, attach, post, sync), and the daily cron syncs issue state. New routes `/feedback/site/triage` and `/feedback/site/triage/issues/$issueId` sit beside the reworked `/feedback` index.

**Tech Stack:** TanStack Start/Router/Query, React 19, Drizzle + D1, Zod, shadcn, Vitest (workers + jsdom pools), Playwright.

**Spec:** `docs/superpowers/specs/2026-10-24-site-feedback-triage-design.md`. Read it first; this plan argues from it and does not repeat its rationale.

## Global Constraints

- One PR from branch `feat/site-feedback-triage`. Every task ends in a commit that is green on its own (`pnpm verify` passes) and is revertable.
- Conventional Commits, scope `ucmc-web` (use `global` only for the env-rename commit, which touches `.github/` and `infra/`). End every commit message with `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.
- `const` only, strict equality, braced control flow, ESM, `strict` TS, `#/` alias. Don't disable ESLint rules.
- Every migration goes through `pnpm --filter ucmc-web db:generate --name <x>` (`--custom` for hand SQL). Never hand-write a migration file or journal entry. Migrations only add.
- The SQL table stays `"feedback"`; the Drizzle export is `siteFeedback`.
- No D1 statement may bind a number of parameters that grows with the data: use `inJsonArray` / `inSubquery` / `insertMany` from `#/server/db`.
- Business logic lives in `*-actions.server.ts`; `createServerFn` shells hold one-line handlers that dynamic-import the action. Every mutation gets a `use-*.ts` hook with an invalidation contract in its header comment. Inline `useMutation` is forbidden.
- Features must not import each other. The `/feedback` index route composes `features/site-feedback` and `features/club-feedback` itself.
- Client gates use `hasPermission` / `hasAnyPermission`; route guards use `effectivePermissionsFor` / `requirePermission`. Never `principal.permissions.includes()` on the client.
- Timestamps are `Temporal`. Calendar dates in GitHub text are rendered in `CLUB_TIME_ZONE`.
- GitHub text attributes members by `users.publicId` only. Never name or email.
- New ids: submissions `sfb_<uuidv7>` (existing `fb_` ids untouched), issues `sfi_<uuidv7>`.
- Env: `SITE_FEEDBACK_GITHUB_TOKEN`, `SITE_FEEDBACK_GITHUB_REPO` (both optional).
- No new cron expression. Sync rides `0 12 * * *`.
- `routeTree.gen.ts` is regenerated by `pnpm --filter ucmc-web build`, never edited.
- Run the narrowest test first: `pnpm --filter ucmc-web exec vitest run <path relative to apps/ucmc-web>`.

## Review Focus

1. **Issue body over GitHub's 65,536-character limit** (for example, 20 linked reports of 5,000 characters each). Expected: filing refuses _before_ claiming the draft, with "Too long for one GitHub issue: unlink reports or trim their text (N / 65,000 characters)". The draft is untouched. Test in Task 11.
2. **Attaching a pull-request number.** The Issues API returns PRs too. Expected: refuse with "#N is a pull request, not an issue". No row is created. Test in Task 11.
3. **Attaching a number already tracked** (filed by the app, or attached before). Expected: reuse the existing `site_feedback_issues` row, with no unique-constraint error and no second row. Test in Task 11.
4. **Filing a draft with no linked reports** (all unlinked). Expected: refuse with "Add at least one report before filing". Test in Task 11.
5. **A submission whose author was deleted** (`created_by` set null, so no `publicId`). Expected: the quote reads "member (deleted)" and the triage row still renders. Test in Task 9 (format) and Task 10 (list).

Filing, in this order (spec §Filing):

1. No config → `not_configured`.
2. Zero links → `no_reports`, with message "Add at least one report before filing".
3. `composeIssueBody(…).length > GITHUB_BODY_LIMIT` → `too_long`, with message "Too long for one GitHub issue: unlink reports or trim their text ({n} / 65,000 characters)".

7. On success: `state='open'`, number, URL, `filed_by`, `filed_at`, `github_synced_at`, and `posted_at` on all links.
8. On `GithubError`: back to `state='draft'` and `filing_started_at = null`, then `github_error` with message `GitHub refused the issue ({status}). Nothing was filed.`

1. `getIssue`. null → `not_found` ("No issue #N in {repo}"). `isPullRequest` → `pull_request` ("#N is a pull request, not an issue").
2. Reuse the row whose `github_number = N`, or insert one (`state` from GitHub, title from GitHub, `summary_md` null).
3. Link the submissions.
4. Post pending.

Post pending: compose one comment from the links where `posted_at` is null, call `createComment`, then set `posted_at` on exactly those links. Zero pending → `{ ok: true, posted: 0 }` without a request.

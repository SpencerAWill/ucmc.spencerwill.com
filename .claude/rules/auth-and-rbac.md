# Auth, identity, and RBAC

## Session & identity

- **Session/principal** lives in `src/server/auth/`. The principal exposes `primaryEmail: string`, `emails: string[]`, and `preferredName: string | null` — the profile's name, `null` until registration is finished. The whole principal is serialized to the client in the session payload, so anything added to it is public to that user. **`preferredName` is what the account chrome shows** (the `UserMenu` label and the avatar's initials fallback), with the email as the fallback for the pre-profile window; the email itself is on `/my/details`. A blank `preferred_name` is normalised to `null` in `loadPrincipal`, since the column is NOT NULL and an empty string would render as an empty label instead of falling back.
- **Multiple verified emails per user**: a `user_emails` table with one `is_primary = 1` row enforced by a partial unique index. `users` has no `email` column — every read joins. A global `UNIQUE(email)` means an address belongs to exactly one account; race safety relies on that constraint via `isUniqueViolation()` in `src/server/db/index.ts`. **All inserts/lookups must go through `src/server/auth/email-normalize.ts`** (`trim().toLowerCase()`). Adding an email is a magic-link round-trip with `intent = "add_email"`; `/verify-email` asserts `session.userId === magicLink.target_user_id` so a stranger can't graft an address onto another account. Promotion is a `db.batch` swap (SQLite enforces partial-unique at statement boundaries). Removing the primary or the last row is blocked.
- **Magic link**: `requestMagicLinkAction` pads the response to ≥500 ms + 0–300 ms jitter to flatten the registered/not-registered timing signal. Only the publicly-enumerable request endpoint gets jitter.
- **Turnstile**: the client widget is gated on `VITE_TURNSTILE_SITE_KEY`; server verification in `features/auth/server/turnstile.server.ts` fails open when `TURNSTILE_SECRET_KEY` is unset.
- **`/register/profile`** accepts a proof cookie (first-time, no `users` row yet) OR a session cookie (returning user with no `profiles` row). `requireRegistrationContext` exposes `{ source, email }`. It collects **only what an exec needs to review the account** — legal + preferred name, phone, UC affiliation, policies ack. The optional parts (emergency contacts, bio) submit empty and are offered on **`/register/pending`**, which mounts `ContactsEditor` + `BioEditor` behind their own Saves. Those write through `submitDetailsFn` / `submitPublicProfileFn`, which require a session but **not** approval — that's what makes them legal before an exec acts, and why the split works without draft state. `/register/pending` redirects an approved principal to `/my/profile` (where the same fields sit beside everything else) and a profile-less one back to `/register/profile`.
- **Officer pre-add ("unclaimed" members)**: `members:manage` officers bulk-add by name + email so off-platform records FK to a stable `users.id`. Unclaimed users have `status="unclaimed"`, `placeholder_name`, `unclaimed_at`, and a primary `user_emails` row with `verified_at = NULL`. The first magic-link click flips them to approved on profile submit, skipping the pending queue — pre-add IS the approval signal. Audit chain: `member.pre_added` → `member.claimed`. Excluded from the public directory and from RBAC role assignment.

## Passkeys (WebAuthn)

`@simplewebauthn/server` + `browser`. The RP is pinned to `WEBAUTHN_RP_ID` / `WEBAUTHN_RP_NAME` / `APP_BASE_URL` (per-env from Pulumi). Each ceremony stashes its challenge in KV at `webauthn:ceremony:<id>` (5-min TTL) and sets a `__Host-ucmc_webauthn` cookie. Finish deletes the KV entry (single-use) and clears the cookie on every branch. Sign-in runs a background conditional-UI ceremony for autofill. The list / add / rename / remove UI is `features/auth/components/passkey-section.tsx` on `/my/security`.

**All three lifecycle mutations are audited** — `passkey.added` / `passkey.removed` / `passkey.renamed`, `targetType: "passkey"` with `targetId` = the row's surrogate `passkey_credentials.id` (never the authenticator-supplied `credential_id`). Renames are audited even though a `nickname` is a cosmetic label with no authentication effect, because the nickname is how a member decides which credential to **revoke**: someone holding a stolen session could otherwise silently relabel passkeys to steer the victim into deleting their own and keeping the attacker's. Metadata carries `{ before, after }`; a no-op rename writes nothing. An empty/whitespace nickname clears the label rather than storing `""`. Repo helpers are scoped by `userId` (`renameCredentialForUser`, `deleteCredentialForUser`) so a caller can only touch their own credentials even if they guess someone else's ID, and both return the affected row so the audit write follows a `.returning()` that proves something actually changed.

## Permissions are DB rows

**Adding a permission needs a migration** — unlike site settings, where a new registry entry is the whole change. Roles, and which permissions each role holds, are runtime-editable at `/access`; the permission catalog itself is not.

**There is no permission-implication mechanism.** Where a write permission should imply its read counterpart (`waivers:verify` → `waivers:view`, `gear:manage` → `gear:inspect`), the OR is expressed at the gate — one shared helper per pair (`requireWaiverViewer`, `requireGearInspector`, `requireAnyPermission` for route guards) rather than `includes() || includes()` scattered across call sites — and the seed migration additionally grants the read permission to the roles holding the write one, so `/access` shows the real grant instead of an invisible implication. Permission-pair constants live beside each other in `features/auth/guards.ts` (`WAIVER_VIEW_PERMISSIONS`, `CLUB_FEEDBACK_PERMISSIONS`, `SITE_FEEDBACK_PERMISSIONS`) because several call sites ask the same question and spelled-out copies drift.

**`roles.displayName` is the only half that may reach the screen; `roles.name` is a slug for comparison.** Directory rows and `MemberDetail` carry `MemberRoleBadge = { name, displayName }` for that reason — they used to carry bare slugs that each badge prettified with `replace("_", " ")` + CSS `capitalize`, which rendered `gear_cave_manager` as "Gear Cave_manager" (non-global replace, first underscore only). **Don't prettify a slug**: it can't recover intended casing, and `capitalize` mangles a real label ("VP of Trips" → "VP Of Trips"), so the badge markup carries no `capitalize` class. The principal carries **`roleDisplayNames`** (slug → label) keyed identically to `rolePermissionMap`, filled in both branches of `loadPrincipal` beside the permission map precisely so a previewable role can't appear in one without the other.

## The `/access` panel

A root-level roles-and-permissions panel — a sibling of `/settings`, not a child of `/members`, sitting next to Settings in the sidebar's bottom utility group. Gated by `roles:manage` plus the `pages.access` kill switch. Named for the umbrella concern rather than either noun it edits so widening its scope doesn't force a route rename; the **permission stays `roles:manage`**, which names the object actually being edited, as do the `roles` table, `RolesListEditor`, and the `role.*` audit actions. It uses the inline `requirePageFlag` primitive (not `staticData`) because it has no auth-guarded parent.

### The role sheet (`RoleEditorSheet`)

Three tabs — Members / Permissions / Details — and **all three stage edits behind their own Save**, each diffing against a baseline snapshotted at open time so a background refetch can't flip Save to dirty. `computeDirty()` derives all three flags from one state snapshot precisely because every tab's save has to ask whether the _others_ are still dirty before auto-closing the sheet. The Permissions tab groups the catalog by `name.split(":")[0]` into an **accordion, collapsed by default with a `granted / total` badge on every header** — the counts make the whole catalog scannable without expanding; the flat always-open stack it replaced is not something to go back to.

**The Members tab writes `user_roles`, so it gates on `roles:assign`, not the `roles:manage` that gates the page.** The two only travel together by seed, so a role delegated just `roles:manage` gets a **read-only** Members tab — deliberate, not an oversight. The server action is **`setRoleMembersAction`**, the role-keyed sibling of the user-keyed `setUserRolesAction` behind `/members/$publicId`; it emits one `role.assigned` / `role.unassigned` row per changed member so the audit page answers "who granted X this role?" the same way regardless of surface. Unclaimed stubs can't hold roles, and you can't drop your own `system_admin` (the sheet also disables that row's trash button, so the affordance is absent rather than present-and-then-rejected).

**It takes an `add` / `remove` diff, NOT the post-state — unlike the Permissions tab beside it, and that asymmetry is deliberate.** The sheet snapshots its baseline when it opens, so a post-state save would delete every member absent from a list that may be minutes stale: grant someone the role from `/members/$publicId` while the sheet sits open, and the next save silently unassigns them with a `role.unassigned` row nobody asked for. Scoping the write to the rows the user actually acted on makes concurrent edits merge instead of clobber. `role_permissions` has no second writer to lose, which is why the Permissions tab keeps its replace-all shape. The action intersects both lists against current membership (so a stale remove or a redundant add writes neither a row nor an audit event) and rejects an id appearing in both. **`ROLE_MEMBERS_DIFF_MAX`** (200, exported from `rbac-fns.ts`) caps each list and is enforced on both sides, the same arrangement as `BULK_ATTEST_MAX`.

The mutation hook invalidates the `["members","detail"]` **prefix**, not one entry: `/members/$publicId` renders roles from `MemberDetail.roles` rather than the per-user assignment cache, and the role-keyed caller knows userIds while those entries key on `publicId`.

**Two roles are read-only on that tab.** `anonymous` hides it outright (it models signed-out visitors and has no members); **`member` is read-only because `setUserRolesAction` force-adds `role_member` back to every approved user**, so an X on those rows would silently no-op — membership follows account status, and the action rejects the role outright rather than letting the two paths disagree. `system_admin` **is** editable here, behind an `AlertDialog` on Save, because it's the one grant that hands over every permission on the site. The member picker is built on `membersDirectoryQueryOptions` rather than `features/gear`'s `MemberSearchCombobox` — that one reads a `gear:loan`-gated server fn, and features can't import each other.

## Role emulation ("View as")

**A client-side _preview_, and the previewed role gates routes as well as chrome.** The contract, in three lines: the previewed role's grants drive every client-side permission question — `useAuth`'s predicates AND the route guards (`requirePermission`, `requireAnyPermission`, `requirePermissionOrNotFound`, `requireViewPermission`); server actions always enforce the **real** principal; and a preview can only ever _narrow_.

That last property is structural, not a check: `rolePermissionMap` is assembled in `principal.server.ts` and holds every role on the site **only** for system admins — for everyone else it holds the user's own roles — and `resolveEmulatedRole` ignores anything absent from it, so a member forging the cookie to `system_admin` falls back to their real set. That lookup is **`Object.hasOwn`, never `in`** — `in` walks the prototype chain, so a cookie of `constructor` / `toString` / `__proto__` would resolve as a real role and `effectivePermissions` would hand back a _function_, which every consumer immediately calls `.includes()` on (in render **and** in server-side `beforeLoad`). The cookie lasts a year, so that is a persistent self-inflicted break.

Guards deliberately do **not** apply the preview to `requireApproved` / `requireAuth` / `requireCurrentWaiver`: those gate account _status_, which no role preview changes, and keeping them real is what stops a preview from locking an admin out of their own `/my/*` pages. Each guard keeps its own failure mode (redirect vs `notFound`) so a preview shows what a real holder of that role would actually hit.

**Every permission-shaped render must ask `hasPermission` / `hasAnyPermission` — never the mere presence of a field in a server payload.** The two agree for a real viewer (the server omits what you can't see) but diverge under emulation, because the server still answers the _real_ principal: a sys admin emulating `member` gets the privileged field and any payload-presence check renders it. That's what hid the waiver card's gate on `/members/$publicId` (`member.waiverStatus ? …`) and why `SponsorGrid` takes `canSeePerks` as a prop. **Client-side gates read `effectivePermissionsFor` (server) / `hasPermission` / `hasAnyPermission` (client) — never `principal.permissions.includes()`**, which bypasses emulation silently. The three `/feedback` routes were the last holdouts: they pick between two surfaces rather than gating on one permission, so they can't use `requirePermission` and had hand-rolled the check.

**The previewed role lives in the `ucmc_view_as` cookie, not `localStorage`, and reaches the app through the session payload** (`getSessionAction` → `emulatedRole`, resolved server-side). That indirection is the entire fix for the original bug: `beforeLoad` runs on the **server** for a hard navigation, where `localStorage` is invisible — so with a client-only store, emulation filtered the sidebar while typing the URL of a hidden page walked straight in. One source, read identically on both sides; `ViewModeProvider` writes the cookie and patches the session cache in place (no refetch) so chrome and guards can't disagree mid-switch. The cookie is intentionally not `httpOnly` (the client writes it) and not `__Host-`-prefixed (that needs `Secure`, which local http dev can't set); it carries no authority, per the narrowing property above. `emulation.ts` sits in `src/server/auth/` beside `session-config.ts` as a plain non-`.server.ts` module precisely so both halves share one cookie name.

**`setEmulatedRole` must call `router.invalidate()` after patching the cache, and that call is load-bearing.** Patching `SESSION_QUERY_KEY` redraws the chrome, but `beforeLoad` only re-runs on navigation or explicit invalidation — so without it the guards never re-evaluate for the page you are _already_ on, and switching to a narrower role while sitting on `/settings` leaves the settings page fully rendered. It is also what makes exiting a preview work at all: clearing the role only redraws the chrome unless the router re-runs the guard that threw the `notFound()`. `view-mode.test.tsx` pins both directions.

**The switcher is a header icon button** (`ViewAsMenu`, `features/auth/components/view-as-menu.tsx`) and **it is its own indicator — there is no banner.** It sits in the header's right-hand icon row between the announcements bell and the avatar, renders only for `isElevated` approved accounts, and lists every key of `rolePermissionMap` minus `system_admin`. Being in the header is what let the amber "Viewing as X / Exit preview" strip go: a previewed role lands on `notFound()`, and `AppLayout` wraps the router's not-found component too — **so the button is still on screen there. Move it anywhere that doesn't render on a 404 and the preview becomes a trap.** While active it takes the banner's amber fill (`bg-amber-100 text-amber-800`), **deliberately not theme-split** the way the banner was: the banner sat on the page background, which inverts with the theme, whereas the header is `bg-primary` in both. The fill is the only visual signal, so **the accessible name carries it in words** (`Viewing as {role}` vs `View as role`, mirrored in a tooltip) — colour alone is SC 1.4.1.

## Member management (`/members`)

The directory and the four management buckets share one surface. Approved is the default tab at `/members`; Pending / Unclaimed / Rejected / Deactivated are real sibling routes under a pathless `_tabs` layout (`routes/members._tabs.tsx`). Approved-only members never see the tab bar (`MembersTabsBar` returns `null` without `members:manage`); each management child route stacks `requirePermissionOrNotFound("members:manage")` so deep links by non-officers surface the notFound boundary instead of redirecting. Each tab owns its own search-param schema — no cross-tab filter carryover.

## Personal namespace (`/my/*`)

`my.tsx` is the auth boundary for everything personal — it runs `requireApproved` once plus the `requireEnabledPages(matches)` walk, so no child re-gates auth. Bare `/my` redirects to `/my/profile`.

The account surface is a **pathless `my._tabs.tsx` layout** holding the "Hi {preferred name}!" greeting and the tab bar over six sibling routes: `/my/profile`, `/my/details` (legal name, phone, **and the verified-email manager**), `/my/contacts`, `/my/waiver`, `/my/security` (passkeys), `/my/preferences`. It's pathless so the greeting and tabs don't leak into `/my/gear`, `/my/gear/cart`, or the planned `/my/dashboard` + `/my/trips`, which are direct siblings that opt out of the chrome. **There is no `/account` URL segment** — the tab group is defined by the layout file, not the URL.

**`/my/details` and `/my/contacts` both write through the one `submitDetailsFn`**, which takes the whole `detailsInputSchema` shape — **each page must pass the other's fields through unchanged from the loaded profile**, or saving from one blanks the other's columns. Emails live on Details rather than Security because they're contact details as much as magic-link targets, which leaves Security to passkeys alone.

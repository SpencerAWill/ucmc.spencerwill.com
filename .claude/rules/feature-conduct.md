# Member conduct records

Why records outlive the account, why the block is a keyed hash, and the retention windows: `docs/adr/0012-conduct-records-outlive-the-account.md`. This file is the rules for changing it.

## Where things go

- **`src/server/conduct/`**: `standing.server.ts` (the one standing predicate, plus `isBlockedEmail`), `email-fingerprint.server.ts` and `retention.ts`. Anything `features/auth`, `features/members` or `features/trips` needs from conduct lives here, because features may not import each other.
- **`features/conduct/server/`**: `record-repo.server.ts` (queries), `record-actions.server.ts` (logic and guards), `record-fns.ts` (one-line `createServerFn` shells), `limits.ts` (Zod schemas and labels).
- **`features/conduct/`**: `/conduct` (records list and detail) and `components/member-conduct-card.tsx`. `routes/members.$publicId.tsx` composes the card; the route may import both features, the features may not import each other.
- **Reports**: members file from the user menu ("Report a conduct concern", `components/report-dialog.tsx`, mounted lazily by `AppLayout` through `components/feedback/conduct-report-launcher.tsx` because `features/auth` cannot import this feature). It shows only when `hasPermission("conduct:report")` and `getPublicFlagsFn().conductReports` (`conduct_reports.submissions_enabled`) hold. The member picker is `searchReportSubjectsFn` (`conduct:report`, public ids and names only, 10 results); **never reuse `searchConductSubjectsFn` there, it returns internal ids.** `/conduct/reports` (`reports-table.tsx`, `triage-actions.tsx`) is the triage list; `/conduct` redirects to it for `conduct:manage` holders and to records otherwise. "Start a record" is `RecordForm` prefilled with the report's subject and `reportIds`.
- **Manager notice**: submitting emails every approved `conduct:manage` holder (or `system_admin`) with a verified primary email and `conduct.report_received` on, except the reporter and the subject, after the batch commits (`notifyManagers`). A failure is logged and never fails the submission. The email (`server/email/conduct-email.ts`) carries a link and no report text.
- **Subject notice**: a warning, suspension or termination emails the subject (`conduct.notice`, not suppressible, so no preference is read) after the batch commits, to their primary verified address; `lift` sends a "lifted" notice with no internal reason. `sendNotice` never throws: no address or a failed send leaves `notice_sent_at` NULL ("Notice not sent" on the detail page). Setting it is what locks the statement (updates are `internalNotes` only). `previewConductNoticeAction` calls the same `conductNoticeEmail`; `RecordForm`'s confirm step fetches it through `previewConductNoticeFn` (POST, so the statement stays out of URLs) and shows the exact subject and text, with issuing disabled while it loads or if it fails. A note has no preview.
- **`/my` card**: `components/my-conduct-card.tsx`, composed by the `/my/_tabs` layout (`my.index.tsx` is only a redirect, so the card lives where it lands and shows on every account tab). `getMyActiveSanctionsAction` (`my-conduct-actions.server.ts`) needs a session and no conduct permission, and returns the caller's own unlifted warnings, suspensions and terminations (a warning or suspension also needs `ends_on` NULL or not past, in `CLUB_TIME_ZONE`; an upcoming one shows) as `{level, statement, startsOn, endsOn}` only. A record whose notice was never sent still shows. The card renders only when the list is non-empty, and ends with `APPEAL_LINE` (defined in `server/email/conduct-email.ts`, re-exported by `limits.ts`; never retype it).
- **Termination enforcement**: after the record batch and the awaited `sendNotice`, `createConductRecordAction` calls `deactivateUserStatements` (`src/server/members/deactivate.server.ts`, shared with `deactivateMembersAction`) with the conduct manager as actor, in its own write. A subject who is not approved transitions nothing. If it throws, the record stands and the action throws "Record saved, but deactivating the account failed…". A new termination for a member who `isTerminated` is refused ("Member already has an active termination"), so a resubmit cannot duplicate the notice or the block. `approveRegistrationsAction` and `reactivateMembersAction` refuse with "Membership terminated; lift the termination first" when `anyTerminated(userIds)` (one `inJsonArray` query) holds, before writing; lifting does not reactivate.
- **`/deactivated`**: `getMyTerminationNoticeFn` (`termination-notice-fns.ts` → `termination-notice-actions.server.ts`) returns `{statement, appealText}` only for the account's own session (`loadCurrentSession`, since the principal loader drops deactivated accounts) or a valid proof cookie whose address matches an unlifted termination's fingerprint (the same join `isBlockedEmail` makes, returning the statement); null for everyone else. `?reason=terminated` with no notice shows the heading and `APPEAL_LINE` without a statement. The body is `components/deactivated-notice.tsx`.
- **Trip sign-up notice**: `getMyConductStandingFn` (`my-conduct-actions.server.ts`) returns `{ suspendedUntil } | null` (null signed out; no record ids, no termination flag, since a terminated member cannot hold a session). `routes/trip-sign-up.tsx` composes it and passes `suspendedUntil` to `TripSignupEmbed`, which shows "You're suspended from club trips until {date}." in an `Alert` and renders no iframe and no new-tab link. `features/trips` cannot import this feature, so `formatPlainDate` lives in `#/lib/date-format` (conduct's `lib/format.ts` re-exports it). An upcoming suspension is not active, so it shows nothing.
- **Pending-queue name hint**: `possibleTerminatedNameMatches(names, exceptSubjectUserId?)` (`standing.server.ts`) compares `lower(trim(subject_name_snapshot))` of unlifted terminations with the trimmed, lowercased names in one `inJsonArray` query, returning a Map keyed by the input name to record public ids. `listPendingRegistrationsAction` sets `conductMatch` only when the real principal holds `conduct:view` (otherwise `null`, never `[]`) and passes the viewer as `exceptSubjectUserId` so a record about them is never named. `PendingTab` shows a "Possible match to a terminated record" link to `/conduct/$publicId` when `hasPermission("conduct:view")` and the list is non-empty. It is a hint: approval is blocked only by `anyTerminated`.
- **Tests**: workers pool for actions, repo and standing; DOM pool for the form, detail and card.

## Rules that are easy to break

- **Standing is decided only in `standing.server.ts`.** A suspension is active `starts_on` through `ends_on` inclusive, in `CLUB_TIME_ZONE`; a termination holds until lifted; a record with `lifted_at` is over. Never re-derive it.
- **Records survive the account.** Every FK from a conduct table to `users` is `SET NULL`, never a cascade, and the subject's name is snapshotted on the record.
- **A viewer never sees records or reports about themselves**, even with `conduct:view` or `conduct:manage`. The filter lives in the repo layer (get returns null, list excludes), not in each caller. `memberConductSummaryAction` returns null for the subject.
- **Only `member_statement` ever leaves exec.** `internal_notes` stays with exec; audit metadata carries the level, transition and IDs only, never text, names or emails. No report text goes in any email.
- **Nothing above a Note is issued from a record referred to SCCS** until an outcome is recorded. The club does not adjudicate a possible SCOC violation.
- **A termination's vote is `votes_for * 3 >= committee_size * 2`**, enforced by both a DB CHECK and the Zod schema.
- **Client gates read `hasPermission("conduct:view")`**, and the member card renders nothing when the fn answers null.
- **Hold no readable list of removed addresses.** `conduct_blocked_emails` holds `emailFingerprint(email)`: HMAC-SHA-256 under the `CONDUCT_EMAIL_KEY` secret, over `normalizeEmail`, lowercase hex. Never store or log the address beside it.
- **A termination fingerprints every `user_emails` row on the account, verified or not**, in the record's own batch through `blockEmailsStatements` (`insertStatements`, so the bind count stays fixed). The fingerprints are computed before the batch, so a missing key throws with nothing written. `lift` deletes them in its guarded batch; a purge leaves them, because the block outlives the account.
- **The block matches only what `normalizeEmail` equates** (trim plus lowercase). Do not canonicalise provider aliases (gmail dots, `+tags`) in the fingerprint or special-case any provider: the block must agree with `user_emails`' unique index, which treats those as different addresses.
- **Three readers, one join**: `isBlockedEmail(email)` (the yes/no every gate asks), `blockedEmailsAmong(emails)` (the same for a list, one `inJsonArray` query, used by pre-add) and `findActiveTerminationStatementByFingerprint` (`features/conduct`, the `/deactivated` statement). All join to `conduct_records` with `level = 'termination' AND lifted_at IS NULL`, so a lifted termination never blocks even if rows remain. Without the key they throw; never catch that into "not blocked".
- **The sign-in and registration gates.** The refusal is `CONDUCT_TERMINATED` and lands on `TERMINATED_HREF` (`/deactivated?reason=terminated`), both in `features/auth/lib/post-sign-in.ts`.
  - `consumeMagicLinkAction` returns it (no cookie, no session) when the owner `isTerminated` in any status (a deactivated one would otherwise reach `/sign-in` with no word of why, and an approved one is left when the deactivation failed), or when no user or an `unclaimed` user owns the address and it is blocked. `/auth/callback` routes it.
  - `webauthnAuthenticateFinishAction` returns it after verification when the credential's owner `isTerminated`; the passkey button and the sign-in autofill route it.
  - `submitProfileAction` repeats the check for a proof or an unclaimed session and throws it before writing, because an older cookie or session predates the termination and the claim approves outright; the profile form routes it.
  - **`requestMagicLinkAction` does not check**: it still sends, so the public endpoint's answer and timing never depend on the block.
- **A blocked address answers as one another account holds**, so the asker learns nothing about conduct: `email_taken` from `requestAddEmailAction` (looked up alongside the ownership check, so both cases do the same work) and `consumeAddEmailAction`, and from officer pre-add (a skip) and `editUnclaimedMemberAction`. A pre-add of a blocked address would otherwise be a way back in.
- **`approveRegistrationsAction` approves only `status = 'pending'`** rows; an unclaimed, deactivated or rejected id in the list is left alone.
- **`CONDUCT_EMAIL_KEY` is required when deployed** (`configurationProblems`) and set to a test value in `vitest.workers.config.ts` and the e2e jobs. Rotating it orphans every fingerprint and so lifts every block.

## Adding things

- **A new level or field**: schema through `db:generate` (additive only), then `limits.ts`, the repo, the action, the form and the detail view together.
- **A new place that needs standing**: call `standingFor` from `src/server/conduct/`; do not import from `features/conduct`.
- **A new mutation**: a `use-*.ts` hook in `features/conduct/api/` that invalidates `conductKeys.all`.
